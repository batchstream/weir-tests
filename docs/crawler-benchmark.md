# Crawler mutation benchmark

This explicit experiment measures database work per completed business product and completed throughput under a fixed database CPU quota. It does not compare total infrastructure cost. Sink is the legacy service that Weir replaces and is not a benchmark path.

The three same-runner paths are native Elasticsearch, current Weir, and optimized Weir. All three receive identical generated product and seller documents, use identical durable completion and query visibility, and share the same exclusively owned Elasticsearch container. The default `single` input uses native single-document Elasticsearch `_update` calls with cached atomic Painless scripts. Weir receives exactly one mutation per SDK `Mutate` call; batching happens inside the server. All paths use the same single-record call shape and business dependencies. An explicit `page` input retains client bulk calls as a separate control. It does not use an unnecessarily weak client-side read/replace cycle.

An exclusive `partial-update` profile reuses the experiment machinery for a separate batching mechanism control. It is not a PSE-equivalent workload and is never pooled with the product/seller results.

## Business data and semantics

The frozen rules come from PSE product/offer merges (`7f36b501cded06a1bcc7484575346bb9c4d6311b`), with the combined reconciliation change in `8725e4743c6ddba66132874e0e0fe9d393ab4a85`. The Weir primitive translation started from the existing independently tested PSE rules at `283940ef442b479440e45b39c86988351b92d7b5`. Every Lua source and the native script has a SHA-256 in the report. The benchmark imports no private PSE data or deployment settings.

One business product comprises one product document and two associated seller documents. The default `-input-shape single -page-size 1` dispatches one business product at a time per goroutine. An explicit `-input-shape page -page-size 20` retains the historical 20-product bulk control; those results cannot stand in for a native single-record baseline. Product documents contain descriptions, prices, country/language unions, three histories initially containing 20 entries, existing offers and new offers. Seller documents contain descriptions, addresses, contacts and tracking ID unions. Worker-owned keys change between two input variants, preventing warmup from turning the measured workload into unchanged writes.

One existing shared seller receives an additional placeholder mutation when `(worker + page) % 100 == 0`. This small shared-key component is explicitly synthetic. It is not an estimate of production key popularity. Other seller documents keep changing throughout the stage, so an automatic no-op visibility barrier is measured in an actively written seller index.

The product and seller data use separate indices, each with one primary shard, zero replicas, `translog.durability=request` and `refresh_interval=1s`. Weir mutations request `QUERY_VISIBLE`; native single-update and page-bulk requests use `refresh=wait_for` and wait for the active primary. Native `retry_on_conflict=3` and both Weir `retry_attempts=4` allow the same four total attempts; ambiguous writes are never automatically replayed by the harness. A page counts as successful only after every product and seller mutation in that page has completed with an application and visibility acknowledgement. A partial page is conservatively counted as failed. It cannot contribute to a qualified comparison.

The generated fixture exercises incoming string replacement, Unicode-safe brand normalization on the supplied ASCII brand, scalar replacement, true/false normalization, history deduplication/caps, incoming offer priority, retained expired offers, stable observation time, UID unions, seller histories, tracking unions and existing-seller placeholder protection. Native Painless implements these exact generated values and rules. This is not a claim that Painless implements arbitrary Lua, or that ungenerated date formats, hostname combinations, nullable values and every production branch have been benchmarked. All fixture URLs use one hostname; URL mapping is absent, so its guard cannot change any generated document.

The independent Go domain oracle reconstructs every seeded document, including untouched and rejected keys, and compares all fields and JSON value types with a normal Elasticsearch search. It checks the expected product/seller index as well. The report stores the verified document count, canonical expected-document hash and acknowledged page ordinals. `audit` reconstructs that hash offline from the page ordinals. Full expected document bodies are discarded after successful verification to keep multi-stage artifacts bounded.

## Workload profiles

`-profiles two-step` is the default and preserves the existing detail-worker reconciliation followed by product and seller updates. The current experiment only tests Weir: PSE is a read-only source of business rules. No business repository changes or migrations are part of this experiment.

`-profiles combined` is an optional controlled workload where every path runs the same single product reconciliation-plus-merge rule. It does not describe a deployed PSE optimization. Differences between current and optimized Weir can be attributed to the server/configuration comparison; they cannot be attributed to combining two PSE calls.

`-profiles combined,two-step` adds an explicit business-call ablation. The two-step profile first reconciles product offers and waits for query visibility, then performs the normal product and seller calls, each with its own visibility wait. The final independent oracle is identical. In the default single-record input, reconciliation must acknowledge before the product update, and the product must acknowledge before its sellers start. The two regular sellers, plus an occasional shared placeholder seller, are submitted concurrently as separate one-record calls and joined before business success. The native connection limit is three times the goroutine count per process, allowing every potential seller to run without an artificial extra native bottleneck. The explicit page control retains products then sellers as separate bulk phases. The detail-worker reconciliation rule does not imply every PSE page performs reconciliation. Compare profiles on the same optimized server to assess removing a product read/merge/write and its visibility wait. This is a separate contribution from the server change.

`-profiles partial-update -input-shape single -page-size 1` isolates server batching from Lua and external read-modify-write. Each independent caller sends one deterministic partial document to one existing product: native `POST /index/_update/id` with `{doc: ...}` versus one Weir `BackendExpression` with the identical body. There are no seller calls, client batches, Lua transforms, or client-side reads. Two keys belong to each sequential worker; `batch_sequence`, title, prices and availability change deterministically so every operation changes its document. Both paths use query-visible completion, request durability, and **zero conflict retries**; the Search Lua retry setting does not apply to backend expressions. All seeded product/seller documents remain in the full-field oracle, including untouched fields, sellers, and rejected keys. This profile must run alone with single input and unlimited adapter concurrency (`-after-max-in-flight 0`), and both Weir paths must have the same binary SHA-256. Its fixture-source hash describes the partial-update contract; it does not label PSE/Lua sources as executed.

`-after-batch-max-wait 20ms` sets only optimized Weir's explicit `batching.max_wait` collection window; the default `0s` preserves immediate execution. The baseline omits this field and receives the zero default. Every stage stores `BatchMaxWaitNS`; offline audit checks the declared path, frozen binary identity, single-record application counts and reconstructed fields. The mechanism report calls out its non-business workload, and observation rows label `logical_unit=partial_update`. Historical `ProductsPerSecond`/`CompletedProductsPerSecond` fields and product-named CPU/latency columns count **one partial-update operation** in this profile. They are not completed PSE business products. The same max-wait option can then be tested independently with the unchanged two-step crawler profile; mechanism and crawler outcomes remain separate.

`-after-max-in-flight 0` keeps adapter concurrency unlimited. Values such as 4 or 16 are explicit experiments and apply only to optimized Weir; the old server never receives an unknown field. `QUERY_VISIBLE` can hold a slot until a refresh completes. A small slot cap may reduce throughput even when the database CPU is idle. The experiment records this outcome rather than assuming the cap improves throughput.

Automatic unchanged-document detection can avoid replacing an existing seller while still issuing an explicit `_refresh` barrier to satisfy query visibility. Compare physical `_refresh` requests, native refresh count/time, merge time, actual index/get work, request/response bytes and database CPU together. Fewer indexed documents alone do not establish a reduction in database load.

## Arrival and completion measurement

Four independently started OS clients each own a driver/SDK pool and multiple goroutine workers. Each child records its input shape and actual native pool limit (three times its worker count for single input; zero for Weir, which does not use the native pool). Pools remain open across warmup, a deterministic document reset, and the timed phase. After both the initial reset and the post-warmup reset, the harness waits for both owned indices to report no current indexing or merging, and unchanged cumulative merge/flush totals and times for at least two consecutive seconds. It samples once per second, fails after 30 seconds without settling, and retains timestamped raw index statistics and wait durations for both waits in each stage. These waits are outside measurement; no force merge is issued. Every path and round receives the same fixture. Paths rotate `ABC`, `BCA`, `CAB` between rounds/cases. The same database survives server binary replacements; server identity and PID are recorded per stage. Settling removes observable ongoing reset work, but cannot make persistent segment history identical or prevent later background maintenance. The retained segment/merge counters and rotating path order expose this remaining limitation.

Fixed-rate experiments schedule page arrivals from absolute timestamps, staggered across processes. Worker completions do not throttle the generator. Each worker has a bounded page queue; a full queue produces an explicit rejected product count. Generator lag, dispatch lag, queue peak, errors, timeouts and uncertain acknowledgements are retained. Latency starts at the planned arrival, includes client queueing and any server aggregation, and ends only after all page mutations are visible. Page latency is also each product's business-completion latency. Histograms include every dispatched page, including failed/timed-out pages; rejected arrivals have no visible completion and are reported separately rather than assigned a synthetic latency. Overloaded stages cannot claim a sustainable arrival rate or a successful-all-arrivals p99. Quantiles use the existing inclusive logarithmic histogram bounds (at most 12.5% plus 1 microsecond bucket approximation).

Saturation experiments use continuously busy sequential workers. Their bounded client queue is still included in planned-to-visible latency. They are not open-loop rate experiments. The complete arrival interval plus every subsequent completion join/drain remains in the throughput denominator. Completions after the arrival interval are counted separately; neither admission nor queueing is counted as success. Warmup is excluded and every seeded record is reset before measurement without replacing the client pools. Reset traffic uses bulk chunks bounded to 8 MiB including action metadata, and every item acknowledgement is checked before continuing; the document set and business workload are unchanged.

The `-modes` flag independently selects `fixed-rate` (the default), `saturation`, or `fixed-rate,saturation`. `-rates none` explicitly disables rate cases; in fixed-rate-only mode at least one rate is required. The manual workflow exposes modes as fixed-rate, saturation, or both. Empty GitHub inputs may fall back to their declared defaults, so use `none` instead of an empty rates input when disabling rates. Run and offline audit share the same selected-case builder.

Concurrency is explicitly bounded to 2048 total workers and 512 workers per OS process; every total must divide evenly between the selected process count. The default remains 128 total workers across four processes. Fixed-rate cases use only the largest `-concurrency-levels` value, so compare 512 and 2048 workers in separate workflow runs rather than passing `512,2048` to one fixed-rate run. Single-record native pools scale to three connections per worker: at four processes, the per-process limits are 384 for 512 total workers and 1536 for 2048. Each worker still has only the configured bounded queue and one active business product. The fixture keeps its existing server queue, pending-record and memory limits; high-concurrency rejection, timeout, overload, OOM or failed settling remains a failed or overloaded measurement. Increasing workers does not demonstrate a database bottleneck. Require measured sustained database CPU pressure before interpreting a run as CPU capacity evidence, and retain unsaturated results.

Select three offered rates only after a short calibration: below, near and above the observed stable capacity. A high rate with rejections is an overload result, not a higher successful capacity. A claimed sustainable rate needs all three rounds without business failures, unknown writes, rejected arrivals or substantial generator lag, plus a declared latency/drain requirement. Do not infer a production capacity from a short preflight.

Each worker records actual application-call attempts at the invocation boundary, including calls that fail or lack acknowledgement. The raw `application_requests` object contains `requests`, `records`, `minimum_records`, `maximum_records`, and `records_per_request`. Concurrent seller calls share only that worker's synchronized ledger. Child and stage `ApplicationRequests` sum the worker ledgers; warmup clients are retained separately from timed clients, including failed warmup evidence. Planned `requested_logical_mutations` remains separate from actual attempted calls, so an early reconciliation failure does not invent subsequent product/seller calls.

Offline audit checks every histogram and worker/child/stage sum. For a successful stage, it independently regenerates the acknowledged business pages, adds the extra reconciliation mutations for the two-step rule, and requires actual submitted records to equal that logical count. In single input every request histogram bucket must be exactly one record, so call count must equal record count. Native attempts refer to `_update` HTTP invocations; Weir attempts refer to SDK `Mutate` invocations. The pinned SDK creates a new `Execute` stream for each call, but the ledger is application-level instrumentation and is not represented as a measured wire counter. Missing acknowledgements remain uncertain and are never replayed by the harness.

## Database observations and evidence

The default `-http-observer disabled` bypasses the transparent HTTP observer for native and both Weir paths, leaving database CPU, native index statistics, completion rules and the full-field oracle unchanged. Its HTTP ledgers are unavailable (`null`), and CSV HTTP counts/bytes remain unavailable rather than becoming zero. The selected observer mode appears in the command receipt, report parameters and observation rows. An absent observer mode in older reports still means enabled; an absent input shape means the historical page input for offline audit. Explicit `-http-observer enabled` places the owned loopback observer between all paths and the database. It records actual physical methods/endpoints, request bodies and response bodies, with monitoring traffic labelled separately. HTTP byte counters exclude headers/framing. They measure database-facing traffic, not Lua/SDK upload bytes. Both the native client and observer disable automatic HTTP compression, matching the Weir Search transport and preventing the observer from introducing database gzip work. The enabled observer uses the same bounded transport and compression policy for all paths; its extra loopback hop is an experiment limitation. Aborted upstream-body copies retain their request attempt, observed partial bytes and failed/aborted counters before the original abort panic is rethrown. Compare failed observer runs with the direct diagnostic control before attributing connection failures to Weir.

When the frozen server exposes Search phase metrics, before/after diagnostics retain `weir_search_http_requests_total` and `weir_search_http_request_duration_seconds` with operation, outcome and visibility labels. Durations run from `client.Do` through body read/validation; bulk duration includes `refresh=wait_for` and cannot be treated as pure indexing time. `weir_search_http_request_records` records the attempted framed mget/bulk request size at the `client.Do` boundary. It does not count acknowledged writes, prove that the network delivered those records, or infer request sizes from adapter invocation size. `weir_search_lua_evaluation_duration_seconds` measures Lua evaluation only. The summarizer retains every labeled counter/histogram bucket delta and emits operation totals/means, wire-record means and Lua time. Missing snapshots/series or reset counters remain `null`, including unused phases on the partial-update path; absence does not prove zero requests. These observations work with the HTTP observer disabled. Use an enabled observer only for a separate short wire-ledger diagnostic, preserving its additional-hop limitation.

Owned Docker cumulative cgroup counters provide database CPU, container network bytes, block I/O bytes and memory samples. The inspected CPU quota is retained. Elasticsearch `_stats` retains indexing/get/search/refresh/flush/merge/translog counters before and after the timed workload. Missing counters stay unavailable rather than becoming zero. Block bytes and filesystem counters do not prove I/O saturation.

`summarize_crawler.py` recomputes sampled database CPU per completed product and budget utilization using valid cumulative-counter intervals clipped to the stage. Sampling coverage is emitted alongside each cost. Treat short-stage or poor-coverage CPU figures as unavailable for conclusions; formal stages should be at least 20 seconds and have at least 80% CPU coverage. The 50 ms generator-lag flag in its CSV is an explicit reporting threshold, not a production SLO. Raw data retains every counter and latency bucket, including failed or overloaded stages. The summarizer does not discard those rows. Its qualification also requires a complete report without cleanup errors. Run the offline auditor first and retain the runner receipt; the CSV is an observation table, not a substitute for source/receipt and full-field validation.

Immutable server preparation receipts contain the full Git commits, clean source state, binary SHA-256, version identity and Go build metadata. The runner receipt also states phase-metric scope, the logical completion unit, the exact seeded-document count (`512 × 1 × 6 + 1 = 3073` for the planned 512-worker single-record control), conflict policies and both max-wait settings before launch. It records the exact command that it executes, client source/clean state, host/kernel/CPU, pinned database image, workflow URL and binary hashes before/after execution. Only newly owned loopback fixtures start, and cleanup receipts retain ownership and removal evidence. Before removing the exact owned Search container, the fixture retains its last 1000 Docker log lines (at most 1 MiB, with a 5-second bound) and a capture receipt; unavailable diagnostics never prevent cleanup. Ordinary unit tests remain offline and never start these services.

## Run

Build exact public source commits without modifying the harness dependency lock:

```sh
python3 scripts/prepare_crawler_servers.py \
  --current 4fe287e5915766ec3f48c8f42abde6b884d89bdd \
  --optimized c3101c6628872345d6fb09b977ce853f25936b79
go build -trimpath -buildvcs=false -o .tools/weir-crawler ./cmd/weir-crawler
```

Use the manual `Crawler database throughput` workflow for Linux Docker measurements. The default main scenario is single input, one product per job, four OS clients, 128 total goroutine workers, observer disabled, and fixed offered rates of 4, 16 and 48 products/s. Page and saturation experiments require explicit selection. Start with the existing two-step rules, one round, 5-second arrival stages, a short warmup and a small matrix. Fix calibrated rates before the three-round 20-second formal matrix. The current experiment does not include a business-call refactor ablation.

A small local functional run (not publishable performance evidence):

```sh
.tools/weir-crawler -concurrency-levels 4 -client-processes 2 \
  -input-shape single -page-size 1 -http-observer disabled -profiles two-step -modes saturation -rates none \
  -rounds 1 -warmup 1s -duration 1s -output results/local/crawler-preflight.json
```

Offline arithmetic and expected-field reconstruction, followed by CSV/JSON observations:

```sh
.tools/weir-crawler audit results/local/crawler.json
python3 scripts/summarize_crawler.py --report results/local/crawler.json \
  --output results/local/crawler-observations
```
