## Fixed workloads and resources

`partial-update`, **512 offered operations/s**, is a mechanism control and **not PSE-equivalent**. Each worker sends one existing product's deterministic partial document through native `_update {doc: ...}` or Weir `BackendExpression` with the identical body. There is no Lua, caller-side read-modify-write, reconciliation or seller call. Every operation changes `batch_sequence`; each sequential worker owns two disjoint keys. Both paths have zero conflict retries. Historic product-named report fields count one partial-update operation here, never a completed crawler business product.

`two-step`, **68 offered business products/s**, independently preserves reconciliation acknowledgement, then product acknowledgement, then separately submitted parallel seller updates and a join. Native uses the frozen Painless rules; Weir uses the frozen Lua rules. The existing occasional shared unchanged seller remains. Native `retry_on_conflict=3` and Weir Lua `retry_attempts=4` keep four total attempts. Failed/ambiguous business work is never replayed by the harness.

Both use four independent OS clients, 512 total workers (128 per process), single-record input, page size 1, fixed-rate absolute arrivals, one queued arrival per worker, and a 10-second planned-arrival-to-business-completion deadline. Native per-process pool ceiling stays 384; it is not a measured connection count. Completed throughput includes every drain; planned-to-visible latency includes queues and aggregation. Client warmup pools survive reset. Every stage verifies **3073 = 512 × 1 × 6 + 1 seeded documents**, including untouched sellers/fields and rejected keys, with the original full-field searchable-source oracle and independent reconstruction from acknowledged ordinals.

Each workflow owns one Elasticsearch database with verified 1 CPU quota, 1536 MiB memory limit, 512 MiB heap, two indices with one primary and zero replicas, 1-second refresh and request translog durability. All paths use `QUERY_VISIBLE` / `refresh=wait_for`. Existing queues (1024 records / 32 MiB), 4096 pending transport records, exchange, memory, connection, retry, deadline and overload safeguards remain unchanged. Failed settling, warmup failure, unknown outcome, cancellation, timeout, native failure, rejection, breaker, OOM and cleanup failure are preserved.

## Measurements and interpretation

Short enabled-observer diagnostics cross-check internal Search attempted HTTP counts against actual observer methods/endpoints, and compare framed mget/bulk record sums to submitted single-record operations where applicable. Histograms represent requests attempted at the `client.Do` boundary, including failed attempts. They do **not** prove network delivery or acknowledged writes. Metadata/mget/bulk/refresh/search timings are client-observed wall time through body read and validation. Bulk `refresh=wait_for` duration includes visibility waiting; it is **not pure indexing time**. Lua timing covers the complete `luaengine.Evaluate` call, including compilation and its internal conversion. It excludes JSON decoding/encoding outside Evaluate and HTTP. Summed concurrent timings may exceed wall-clock elapsed time and cannot be subtracted to obtain exclusive critical-path time.

Internal outcomes can classify a canceled/timeout request that the observer later finishes differently. Server metrics are sampled at two boundaries and may miss in-flight tail events on unsuccessful stages; retain differences and classify the stage unqualified, rather than adjusting counters to match. Missing series/snapshots or reset counters stay unavailable, not inferred zero. Histogram boundaries and inclusive logarithmic client latency upper bounds retain their precision limits (client quantiles within 12.5% plus 1 microsecond). Diagnostics are for correctness/count consistency only and incur the observer's extra loopback hop. Formal observer-disabled stages independently measure real database CPU, native command statistics, HTTP phase/record metrics, p99, drain and completion. Adapter invocation sizes are reported separately from actual framed HTTP sizes.

Freeze analysis code and checks before reading formal results. Preserve every available artifact with compressed and uncompressed SHA-256 and byte length, source and command receipts, owned manifests/logs/config/cleanup and original whole-report Go audit exit/output. A failed or incomplete report must remain failed, even if some preceding rows are independently useful diagnostics. Raw rows, failed warmup and aborted stages remain visible. Do not pool absolute CPU/throughput across workflows or between the two logical units.

## Formal gates fixed before results

Each formal workflow requires frozen clean source/receipts/config, all nine complete measured stages after 30s warmup / 20s arrivals, live before/after `weir_store_batch_max_wait_seconds` attestation of 0 or 0.02 and `weir_store_active_executions_limit=0` for every stage, successful owned cleanup, full 3073-document field verification, independent hash reconstruction, original complete-report Go audit, complete process/worker/application/histogram arithmetic, and clipped database CPU sample coverage >=80%. All-arrivals qualification additionally requires zero failed, unknown, timed-out or rejected work, offered equals completed, p99 planned-to-visible upper bound <=5s, drain <=3s and maximum generator lag <=50ms. These limits are experimental gates rather than production SLOs.

A strict lower-database-CPU claim at comparable completed throughput requires **both compared paths to pass every formal gate in all three paired rounds**, completed-QPS ratio in `[0.95, 1.05]` in each round, and CPU ms/completed logical unit lower in each round. Compare candidate/baseline and each Weir/native independently. A smaller response, fewer HTTP requests, larger batches or lower concurrent phase time is a mechanism observation, not itself a CPU/throughput improvement. Extra Weir CPU and total infrastructure cost are not adoption gates.

Capacity or database-bottleneck claims additionally require actual sustained database CPU in each relevant formal round: at least five valid cumulative-counter intervals, >=80% clipped coverage, mean >=90% of verified quota, and time in intervals >=90% CPU covering >=80% of the **whole elapsed measurement including drain**. Do not extrapolate missing intervals. Equal quotas are not equal actual database load. No maximum capacity, confidence interval, production throughput or distributed-network claim follows automatically. No additional rate matrix is part of this plan.
